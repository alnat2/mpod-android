# mpoddy Current Tasks

Единый живой backlog Android-приложения `mpoddy` и инструкция по его ведению.

Последняя редакция: 8 сентября 2026 года.

## Назначение файла

Этот файл хранит только актуальные открытые задачи, их порядок, текущий этап и следующего исполнителя. Он является оперативным дополнением к [`android-delivery-plan.md`](android-delivery-plan.md): delivery plan определяет продуктовый контракт, приоритеты и release policy, а этот файл определяет, что именно делается следующим.

Закрытые задачи удаляются из этого файла. История завершённой работы остаётся в Git и профильных отчётах. Неверные или снятые выводы не сохраняются как задачи и перечисляются только в защитном разделе в конце файла, чтобы их не вернуть без новых фактов.

## Роль Team Lead

Team Lead отвечает за продуктовый приоритет, качество кандидата и последовательность работы.

Team Lead:

- начинает с основных пользовательских сценариев и очевидных дефектов;
- отделяет подтверждённые пользовательские проблемы от предположений и технического долга;
- поддерживает этот файл в актуальном состоянии;
- активирует только одну задачу и одного исполнителя одновременно;
- выдаёт разработчику узкую задачу на один подтверждённый дефект;
- требует regression-тест для каждого исправленного P0/P1 и для воспроизводимых P2;
- проверяет точный diff и результаты тестов до сборки нового APK;
- разрешает commit/push и выпуск кандидата только после повторной продуктовой приёмки.

Team Lead не должен:

- заменять продуктовый smoke глубоким аудитом proxy-логов, cache miss или редких гонок;
- считать статический анализ доказательством пользовательского дефекта;
- объединять несколько независимых дефектов в одно неограниченное исправление;
- начинать рефакторинг, миграцию package name или архитектурную чистку без влияния на активный сценарий;
- включать в commit посторонние файлы или чужие незакоммиченные изменения;
- коммитить или пушить текущий кандидат до отдельного решения по точному составу изменений.

## Как работать с файлом

1. Одновременно активна только одна задача и назначен только один следующий исполнитель.
2. Активная задача всегда находится первой и содержит полный готовый текст, который можно без дополнительных пояснений целиком передать исполнителю. Краткое управленческое описание не считается заданием. Обязательны: исходное состояние и точные идентификаторы, источники, разрешённый scope, запрещённые действия, ожидаемые проверки, формат результата, критерий завершения и следующий переход.
3. В заголовке активной задачи обязательно указывается время её последнего содержательного обновления в формате `ДД.ММ.ГГГГ ЧЧ:ММ TZ`, например: `## 1. АКТИВНО — 06.09.2026 13:23 MSK — Название задачи`. При любом изменении задания, статуса, замечаний review или критерия следующей сдачи timestamp в заголовке обновляется. По нему Team Lead и исполнитель определяют, видят ли они актуальную редакцию задачи.
4. Остальные задачи имеют статус `НЕАКТИВНО` и выполняются строго сверху вниз с учётом приоритета.
5. Новый подтверждённый P0/P1 из активного product smoke вставляется перед существующими P2/P3 и оформляется отдельной задачей.
6. Диагностическая задача не меняет production-код. Разработка начинается только после воспроизведения или достаточного доказательства причины.
7. Разработчик возвращает точный список файлов, проверки и локальный commit только тогда, когда Team Lead отдельно разрешил создание commit.
8. После разработки Team Lead выполняет code review; затем тестировщик проверяет исправленный сценарий и короткую регрессию связанных основных сценариев.
9. При FAIL дефект не исправляется тестировщиком на месте. Возвращаются шаги, expected/actual и evidence, после чего Team Lead формирует узкую задачу.
10. После полного закрытия задача удаляется из файла, а статусы связанных строк в [`android-user-scenarios.md`](android-user-scenarios.md) обновляются.
11. Временные fixture, дампы, скриншоты и логи не добавляются в Git без явной доказательной ценности.

## Стандартный жизненный цикл дефекта

1. **Продуктовая проверка:** воспроизвести проблему в основном пользовательском сценарии.
2. **Декомпозиция:** определить один дефект, затронутый контракт и минимальный объём исправления.
3. **Regression first:** добавить тест, который воспроизводит проблему или надёжно защищает исправляемую границу.
4. **Разработка:** исправить только подтверждённую причину.
5. **Code review:** проверить diff, корректность состояния, тестовую ценность и отсутствие посторонних изменений.
6. **Повторная приёмка:** проверить исправленный сценарий на Android и короткий smoke его зависимостей.
7. **Закрытие:** обновить сценарии и backlog; только принятый кандидат допускается к commit/push/release-процедуре.

## 2. НЕАКТИВНО — Синхронизировать выбранную подписку и её выпуски

**ID:** `MPOD-BUG-01`
**Направление:** Compose UI / subscriptions.
**Приоритет:** P1, release blocker.
**Статус:** подтверждён на физическом телефоне с частотой 3/3 и локализован в коде; ожидает `MPOD-OPS-01`.
**Следующий исполнитель после активации:** Android-разработчик.

### Подтверждённая проблема

`SubscriptionsScreen` определяет карточку через `pagerState.currentPage`, а детали через `pagerState.settledPage`. Во время swipe карточка `Веб-стандарты` показывается вместе с summary/list от `Test Podcast Alpha`; после Show all карточка `Веб-стандарты` остаётся со строками `6 Minute English`; после Mark listened карточка `Test Podcast Alpha` показывается со списком Podlodka. Mutating actions могут получить разные podcast ID. Evidence и точные шаги сохранены в [`android-product-smoke-report-2026-09-07.md`](android-product-smoke-report-2026-09-07.md).

### Требуемое исправление

1. Ввести один authoritative selected podcast/page для карточки, счётчиков, эпизодов и всех podcast-scoped действий.
2. Сохранить корректное wrap-around поведение карусели и переключение Show all/Show unlistened.
3. Не менять дизайн карточки, порядок подписок или продуктовый контракт.
4. Добавить regression-тест минимум с двумя подкастами и явно различающимися выпусками.
5. Проверить состояние во время drag, после settle, на искусственных крайних страницах и после изменения visibility-filter.
6. Проверить, что Refresh, Unsubscribe и Mark all listened получают ID того же подкаста, который показан выбранным.
7. Выполнить targeted unit/Compose tests, затем полный обязательный Android gate и `git diff --check`.

**Критерий code review:** в любой отображаемый момент карточка, summary, episode list и действия согласованы по одному podcast ID; regression-тест падает на прежней реализации.

**Будущая phone-приёмка:** быстро и медленно пролистать минимум три подписки, задержать жест между страницами и выполнить безопасное действие на выбранной карточке; чужие выпуски не появляются ни постоянно, ни транзитно.

## Не возвращать в backlog без новых фактов

Следующие выводы кодового анализа проверены и не считаются текущими задачами:

- package/namespace `com.example.mpod` при release `applicationId = com.prod.mpod`;
- переименование всего Kotlin package;
- «неверные» иконки `-10/+15`, выведенные только из имени vector resource без фактической визуальной ошибки;

- неполный `AppSettings` в `saveProxySettings()`, пока proxy selector читает только proxy-поля;
- дублированный SQL в `PlaylistDao` для разных return types (`Flow` и `List`);

- headset/noisy-route до нового решения владельца продукта.
