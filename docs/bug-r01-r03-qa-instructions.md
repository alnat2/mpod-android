Проверить время отчёта и serial: результаты должны относиться к текущему запуску. Если каталог отсутствует, сначала выяснить, запускались ли тесты, а не использовать старый отчёт.


```sh
cp -R app/build/outputs/androidTest-results/connected "$QA_EVIDENCE/connected-results"
```

Проверить не только exit code, но и реально выполненные имена тестов:

| Класс / тест | Что должно быть доказано |
|---|---|
| `UnsubscribeDownloadTest.slowBody_undoThenFinalUnsubscribe_removesRoomQueueAndFiles` | Файл действительно начал записываться; Undo не отменяет загрузку; после окончательной отписки нет подкаста, эпизода, playlist row и файлов; владелец завершён; нет повторного запроса загрузки |
| `UnsubscribeDownloadTest.deleteFailure_keepsRealRoomLink_andUiRetryRepeatsUnsubscribe` | При отказе удаления остаются файл, запись и путь; видна ошибка; Try again после снятия отказа завершает отписку |
| `SubscriptionsQueryTest.queryCountForOneAndThirtyPodcastsIsConstantComparedWithLegacyNPlusOne` | Старый путь: 1/30 отдельных запросов эпизодов; новый: 1 общий запрос для обоих размеров; обновление допускает initial + invalidation SELECT, без N+1 |

Ограничения: тесты отписки используют fake настроек и не запускают настоящий PlaybackService/ExoPlayer. Audio payload теста предназначен для проверки записи файлов, а не прослушивания. Поэтому шаги 5–7 через приложение обязательны. Отказ удаления уже воспроизводится через test fixture — не имитировать его изменением прав production-каталога.

## 5. R01: отписка во время загрузки и воспроизведения

### R01-A. Медленная загрузка, Undo и окончательное удаление

Включить задержку между audio chunks; она применяется к новым HTTP-запросам и не меняет уже начавшийся ответ:

```sh
curl --fail --silent --show-error -X POST http://127.0.0.1:8765/__control -H 'Content-Type: application/json' --data '{"audio_delay":0.5}'
```

1. Записать ID подкастов A/B и выбранных выпусков, исходный состав очереди и файлы (команды в шаге 8).
2. Добавить по нескачанному выпуску A и B в очередь. Автоскачивание production-кода имеет debounce около 15 секунд. Дождаться реальной записи `.tmp`, подтвердить рост размера двумя снимками. Наличие строки в очереди само по себе не доказывает старт загрузки.
3. На карточке A нажать Unsubscribe. До истечения 15 секунд нажать Undo.
4. Проверить: A остался; выпуск и очередь сохранены; отмена отписки не остановила фоновую загрузку A; B не затронут. Не требовать, чтобы `.tmp` обязательно оставался: он мог успеть превратиться в готовый файл. Сверить файлы/Room и журнал сервера.
5. Для следующего удаления обеспечить заново подтверждённую активную загрузку A и B. Если первоначальные уже завершились, выбрать другие ещё не скачанные выпуски. Убедиться, что их передача продолжается в момент окончания countdown.
6. Запустить воспроизведение выбранного выпуска A. Подтвердить настоящий MediaSession в состоянии PLAYING и рост позиции, затем сразу нажать Unsubscribe и не нажимать Undo.
7. Снять evidence до окончания countdown и после завершения удаления. До окончания 15 секунд A остаётся в Room; удаления по отписке ещё нет. После завершения операции A исчезает, его выпуски и playlist rows удалены, файлов всех его эпизодов нет. Старый текущий эпизод больше не воспроизводится и не остаётся в MediaSession/очереди.
8. B остаётся подписанным; его очередь и файл/загрузка не удалены отпиской A. Нормальное завершение скачивания B допустимо. Не требовать автозапуска B: проверяется отсутствие удалённого A и согласованность оставшейся очереди.
9. Через 20 секунд повторить проверку файлов и Room для заранее записанных ID A: поздних `.tmp` и готовых файлов нет, удалённый эпизод не вернулся. После relaunch приложения результат сохраняется.

Важно: фиксировать состояние непосредственно перед фактическим удалением. Если A естественно завершился за 30 секунд до отписки либо загрузка завершилась раньше countdown, соответствующий сценарий не доказан — повторить с другим нескачанным выпуском и скорректировать последовательность. Buffering не считать подтверждением продолжающегося PLAYING. У одного URL могут быть отдельные запросы плеера и Smart Listening; не требовать ровно одного HTTP-запроса в ручном сценарии с playback. Проверка одного запроса относится только к автоматическому тесту без плеера.

**PASS:** подтверждены активная загрузка, Undo, удаление после окна, отсутствие данных и поздних файлов A, согласованность настоящего Player и сохранность B. Если UI исчез, но Room/files/MediaSession не проверены, полного PASS нет.

### R01-B. Уже скачанный файл и локальное воспроизведение

Вернуть быструю передачу для новых запросов:

```sh
curl --fail --silent --show-error -X POST http://127.0.0.1:8765/__control -H 'Content-Type: application/json' --data '{"audio_delay":0}'
```

1. Заново добавить A. Добавить выпуск в очередь и дождаться Downloaded, `isDownloaded=1`, непустого `localFilePath` и существующего непустого файла.
2. Запустить этот выпуск с начала. Подтвердить PLAYING и рост позиции. Проверить, что плеер использует локальный файл: сверить доступную диагностику источника и отсутствие нового audio GET после старта; при недостаточных данных так и указать.
3. Сразу выполнить Unsubscribe без Undo; не допустить естественного окончания до истечения окна.
4. Проверить удаление A/его эпизодов/playlist rows, отсутствие связанного файла, отсутствие удалённого A в Player, сохранность B. Через 20 секунд повторить проверку и выполнить relaunch.

**PASS:** ранее сохранённый файл удалён вместе с подпиской; UI, Room и playback согласованы; B не затронут. Проверка отказа удаления/Retry принимается по автоматическому тесту шага 2 и записывается отдельно.

## 6. R03: обновление подписок при продолжающемся playback

1. Вернуть `audio_delay=0` и добавить A заново, если его нет после R01. Для A установить исходную revision 1 до добавления, если сервер ранее переключали. Использовать свежую подписку: понижение revision в RSS не гарантирует удаления ранее импортированных выпусков из Room.
2. Убедиться, что у A 3 выпуска в порядке 3, 2, 1. Записать фактические listened/downloaded и очередь. Выбрать Show all, чтобы фильтр Unlistened не скрывал проверяемые строки.
3. Подготовить скачанный выпуск B и запустить с начала при скорости 1.0x. Снять MediaSession/позицию; перейти в Subscriptions. Позиция растёт, паузы из-за перехода нет.
4. Пока B воспроизводится, добавить новый выпуск A через сервер:

```sh
curl --fail --silent --show-error -X POST http://127.0.0.1:8765/__control -H 'Content-Type: application/json' --data '{"revision":2,"audio_delay":0}'
```

5. Нажать Refresh на A. Новый `QA race episode 4` появляется без ухода с экрана/повторного открытия. Порядок — 4, 3, 2, 1; всего 4 выпуска. Если все были непрослушанными, непрослушанных тоже 4; иначе счётчик увеличивается на один относительно baseline. B продолжает PLAYING с растущей позицией.
6. Добавить новый выпуск A в очередь: состояние действия становится Remove from playlist. Дождаться автоматической загрузки: Downloaded появляется без переоткрытия экрана. Удалить выпуск из очереди: состояние действия возвращается к Add to playlist.
7. Пометить один непрослушанный выпуск A прослушанным. Счётчик уменьшается на один; в Show all выпуск остаётся с новым состоянием, в Unlistened скрывается. Не использовать для этого текущий играющий выпуск B.
8. Сравнить результат с Room. Проверку metadata и пустого подкаста принять по `liveRoomProjectionDeliversRssMetadataFlagsQueueAndEmptyPodcasts`: существующий сервер не создаёт пустой RSS, не нужно ради QA редактировать БД приложения.

**PASS:** playback не прерывается из-за перехода/Refresh; новый выпуск, порядок, счётчики и признаки обновляются без переоткрытия. Проверку нового выпуска и playback выполнить в пределах 30 секунд B. Дальнейшие действия при необходимости проводить с заново запущенным B; естественное завершение записывать отдельно, не выдавать за сбой Refresh.

## 7. R03: принять измерение запросов и mapping

Не оценивать устранение N+1 только по субъективной скорости UI. В результатах трёх `SubscriptionsQueryTest` должны присутствовать измерения для 1 и 30 подкастов: один общий запрос независимо от количества и отсутствие запросов эпизодов по одному подкасту. Допустим дополнительный invalidation SELECT. Запрос после UPDATE позиции сам по себе не FAIL.

Отсутствие повторного дорогого mapping равных данных проверяет JVM-класс `SubscriptionsProjectionTest`; настоящая Room отдельно доказывает равенство проекций. Если кандидат совпадает с уже проверенным кодом `60bd3f5`, можно сослаться на независимый полный прогон 193/193 от 01.10.2026. Если код изменился или нужен собственный targeted-прогон:

```sh
./gradlew :app:testDebugUnitTest --tests 'com.example.mpod.ui.screens.subscriptions.SubscriptionsProjectionTest' --rerun --console=plain > "$QA_EVIDENCE/projection-tests.log" 2>&1
```

Ожидается 2/2 PASS. Сохранить отчёт до последующих unit-прогонов. Не объявлять этот targeted-прогон новым полным 193/193.

Если тестовый эмулятор содержит посторонние данные, сохранять только относящиеся к сценарию строки и обезличивать логи перед передачей.

Состояние настоящих MediaSession; в отчёте выделить сессию `com.prod.mpod`, текущий эпизод, playback state и position. Сделать минимум два снимка для доказательства роста позиции:

```sh
"$QA_SDK/platform-tools/adb" -s "$QA_SERIAL" shell dumpsys media_session > "$QA_EVIDENCE/r01-before-media-session.txt"
```

Подкасты, эпизоды и очередь. До удаления записать ID всех эпизодов A, включая не добавленные в очередь:

```sh
"$QA_SDK/platform-tools/adb" -s "$QA_SERIAL" shell 'sqlite3 -readonly -header -column /data/user/0/com.prod.mpod/databases/mpoddy.db "SELECT id,title,feedUrl FROM podcasts; SELECT id,podcastId,title,isListened,isDownloaded,localFilePath FROM episodes; SELECT episodeId,position FROM playlist_items ORDER BY position;"' > "$QA_EVIDENCE/r01-before-room.txt"
```

Каталог загрузок: файлы именуются `ep_<episodeId>_...`; проверить все заранее записанные ID A, а не только текущий эпизод. До первой загрузки каталог может отсутствовать; это не ошибка само по себе. После удаления важно отсутствие принадлежащих A файлов, а не пустота всего каталога — файлы B должны сохраниться.

```sh
"$QA_SDK/platform-tools/adb" -s "$QA_SERIAL" shell ls -la /data/user/0/com.prod.mpod/files/podcasts > "$QA_EVIDENCE/r01-before-files.txt"
```

Дополнительно к снимкам сохранить соответствующий интервал `fixture/requests.jsonl` с путями, временем начала/завершения/разрыва запросов. Серверный запрос сам по себе не доказывает, что файл записан на устройстве; сопоставить его с `.tmp`, Room и UI. Если сохраняется logcat, не очищать существующий буфер и не включать в отчёт секреты, proxy credentials или чужие URL.

## 9. Вердикт, отчёт и завершение

Для R01 и R03 вынести независимые вердикты:

- **PASS** — все обязательные сценарии соответствующего пункта выполнены, приложены evidence, ограничения явно указаны.
- **FAIL** — наблюдается нарушение ожидаемого поведения. Указать воспроизводимые шаги, фактический и ожидаемый результат, commit, ID эпизодов, момент сбоя и доказательства. Продолжать исправление в том же баге.
